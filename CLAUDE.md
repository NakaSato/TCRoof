# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

TCRoof is an iPad-first SwiftUI app (iOS 17, bundle `com.tcroof.internal`) for a solar installer: jobs, install plans, device scans, install logs, and the **solar site survey** module, which produces the company's PDF report and Excel workbook. UI text is Thai.

## Build and test

- **Package logic and tests (fast, macOS):** run from `TCRoofKit/`
  - `swift build`
  - `swift test` (or `swift test --parallel`: about half the time, one process per test, so a test can't lean on another's state)
  - `swift test --filter InverterStationTests` (one class) or `swift test --filter InverterStationTests/testOutdoorRoom` (one test)
- **`TCRoofUI` and the app:** these are wrapped in `#if canImport(UIKit)`, so `swift build` on macOS does **not** compile them. Verify UI changes with xcodebuild:
  ```
  xcodebuild -project TCRoof.xcodeproj -scheme TCRoof -destination 'generic/platform=iOS Simulator' -derivedDataPath <scratch>/DerivedData build
  ```
  Always pass your own `-derivedDataPath`. The user keeps Xcode open, and a CLI build in the shared DerivedData locks Xcode's `build.db`. Reuse the same path between builds: a clean build takes over 10 minutes, so run it in the background.
- **Linux (cloud sessions):** `TCRoofCore`, `ExcelExport` (with `CZlib`), `PVYield` and `ModuleRules` build there (the rest needs Apple frameworks). `tools/linux-swift/test.sh` (takes `swift test`'s arguments: `--parallel` for everything, about 2 minutes, or `--filter HourlyYieldTests`) links them into a small package (every target line copied from `Package.swift`, with `tools` and `Project_Plan_TCRoof` links where the tests look) and runs their tests at Bangkok time (`TZ`, as the tests assume); the session hook (`.claude/hooks/session-start.sh`) installs Swift in `/opt`, puts it on `PATH` and builds the package once. Keep `TCRoofCore` building there: guard Apple-only imports with `#if canImport(…)` (`DevKey`'s PBKDF2 and `FormHash`'s SHA-256 have pure-Swift fallbacks), and give long numeric expressions explicit types, since Linux's type checker gives up sooner. In tests, don't create a test case to borrow its helpers (`XCTestCase()` doesn't exist there; DXF reading is `DXFRead`). Linux Foundation lists nothing in a folder reached through a symlink, so resolve one first (`MPTemplates.cases`). `FloodLookupStubTests`' cases where the lookup fails skip on Linux: `fetch` then cancels the other years' requests, and Linux Foundation's cancelled `URLSession.data(for:)` never returns.
- **Lint:** there is no SwiftLint or swift-format config and no CI; the checks are `swift test` and the xcodebuild build.
- **Toolchain:** if `swift build` fails on `actool`, or `xcodebuild` says the active developer directory "is a command line tools instance", prefix the command with `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer`.
- **Secrets:** `Config.xcconfig` includes the git-ignored `Secrets.xcconfig` (copy `Secrets.example.xcconfig`) for `GISTDA_API_KEY`. The app builds without it.

## Architecture

**App target (`TCRoof/`)** handles Google sign-in (`Auth/`), SwiftData models, Firestore sync (`Sync/CloudSync.swift`) and the non-survey screens. Firestore access is limited by `firestore.rules` (Firebase project `tcroof-1564c`): only accounts with a `members/<email>` document, and only the collections the app syncs, so a newly synced collection needs a rule. A manager (`users.manage`) edits that list in Settings › `สมาชิกทีม` (`TCRoof/Auth/MembersView.swift`): invite a Google account with a role and send the invite through the share sheet (with `config/app.installLink` when set), change a role, remove someone; the rules refuse a manager's own document. Sign-in checks the same list (`GoogleSession.signIn`): an account without a `members/<email>` document is signed out again (offline, only one this device has seen listed gets in), an account removed from it is signed out at the next sync (`MemberRole.onRemoved`), and when a different account signs in the previous one's records on the device are removed before sync starts if the new account is external (`LocalData`, which also forgets sync's known list so nothing is deleted in Firestore); a team account keeps them and takes over sync's known list (`CloudSync.carryKnown`). Settings' `สลับบัญชี` and `ออกจากระบบ` first wait for Firestore to confirm this account's writes (`CloudSync.flush`) and ask before going on without them, and Google sign-in uses a fresh browser session with the account picker, so on a shared iPad the next person isn't offered the previous one's account. Photos travel through Google Drive, not Firestore: survey photos by `SurveyModel.autoUploadPhotos` / `fetchMissingPhotos` (the Drive ids in the job JSON), and daily-report, ICL and IEC photos by `Sync/PhotoSync.swift` (a daily report's drawn signatures too: `PhotoAsset`s of the log tagged `signature.engineer` / `signature.inspector`, left out of `sortedPhotos` and printed on the DAILY REPORT's page 3), which uploads them into the job's `TCRoof Projects` folder and syncs one `photos` document per photo (its Drive id and owner) for the other devices to download. Every job folder is shared read-only with everyone who can open the job (the team, from the directory or `config/app.driveShareWith`, and the job's contractors and supervisor; `SurveyModel.shareJobFolder`, `DriveReaders`), after each upload and in each `PhotoSync` pass, each address once per folder, so every photo a report prints downloads on every member's device. The same pass carries a station's imported MP plan workbook (`Job.scheduleWorkbook`): it uploads to the job's `แผนงาน MP` folder, its Drive id rides on the job record (`scheduleWorkbookDriveID`), and the other devices download it so any of them can export the plan file. It hosts the survey module via `Views/Survey/` (`SolarSurveyEntry`, `PWASurveyLink`).

**Travel log** (`TCRoof/Travel/`): `Trip`, `Expense` and `ClaimMonth` belong to one person (`ownerEmail`); `CloudSync` listens to the signed-in person's only (`ownerEmail ==`), pushes them in their own batches and skips another account's left on a shared iPad (`OwnedRecord`); the rules let the owner write them and managers read them, never contractors. Receipts stay on the device until the month is submitted (`ClaimExport.upload`, the person's Drive `เบิกค่าใช้จ่าย/<ปี-เดือน>/<ชื่อ>/`), then their Drive ids travel on the records. A manager approves a submitted month or sends it back with a reason in `ตรวจใบเบิกของทีม` (`ClaimReviewScreen`, reading the person's records from Firestore while open): the decision is a `claimReviews` document (`TravelClaim.Review`) only managers write, never on their own claim, valid for that submission only; the claimant sees it (`ClaimReviews`, from `CloudSync`), is notified of a new one (`ClaimNotification`, a tap opens the month; also in the bell for 7 days) and can't withdraw an approved month. A submitted month's folder is shared read only with `config/app.claimShareWith`.

## MCP Tools: code-review-graph

The server runs the `code-review-graph` binary from `.mcp.json`; install it with `uv tool install code-review-graph`. If it fails to connect, use grep and Read instead.

**This project has a knowledge graph. Start with the code-review-graph
MCP tools to narrow scope, then read the source.** The graph is cheaper than scanning files and
gives you structural context (callers, dependents, test coverage) that file search cannot.

### When to use graph tools FIRST

- **Exploring code**: `semantic_search_nodes_tool` or `query_graph_tool` instead of Grep
- **Understanding impact**: `get_impact_radius_tool` instead of manually tracing imports
- **Code review**: `detect_changes_tool` + `get_review_context_tool` instead of reading entire files
- **Finding relationships**: `query_graph_tool` with callers_of/callees_of/imports_of/tests_for
- **Architecture questions**: `get_architecture_overview_tool` + `list_communities_tool`

### Verify in the source

- Narrow scope with the graph, then read the source. Do not change code from graph output alone.
- For any non-trivial change, read the implementation and the relevant tests before concluding.
- Verify the exact source when touching behavior, database logic, migrations, retries, fallbacks,
  recovery, or compatibility code.
- When the graph and the source disagree, the source wins. The graph may be stale or may not
  model that relationship.
- An empty graph result can mean "not indexed" or "not statically visible", not "does not exist".
  Uncommitted new files are often missing; fall back to grep.

### Key Tools

| Tool | Use when |
| ------ | ---------- |
| `detect_changes_tool` | Reviewing code changes — gives risk-scored analysis |
| `get_review_context_tool` | Need source snippets for review — token-efficient |
| `get_impact_radius_tool` | Understanding blast radius of a change |
| `get_affected_flows_tool` | Finding which execution paths are impacted |
| `query_graph_tool` | Tracing callers, callees, imports, tests, dependencies |
| `semantic_search_nodes_tool` | Finding functions/classes by name or keyword |
| `get_architecture_overview_tool` | Understanding high-level codebase structure |
| `refactor_tool` | Planning renames, finding dead code |

### Workflow

1. The graph auto-updates on file changes (via hooks).
2. Use `detect_changes_tool` for code review.
3. Use `get_affected_flows_tool` to understand impact.
4. Use `query_graph_tool` pattern="tests_for" to check coverage.
